01 Panorama general y puertos

Qué es auth-ms y las tres formas de conectarse a él

auth-ms es el microservicio central de identidad y autorización (IAM) de BPONET. Administra usuarios, roles, permisos, módulos, empresas (tenants), sesiones y políticas por empresa. Todas las demás aplicaciones del ecosistema consumen sus servicios en lugar de mantener su propia lógica de autenticación.

Arquitectura de integración
NavegadorApp externa (Angular/React)
⇄
auth-msIdentidad · Autorización · TenantsREST 3010 · TCP 3011
→
MongoDBUsuarios · Sesiones · Policies
El navegador habla solo por HTTPS/REST con el access token. Los backends hablan por REST con clave de servicio o por TCP con serviceKey.

Principio de diseño del token El JWT contiene solo identidad (_id, name, email, company, tenantId, isSuperAdmin). El árbol de autorización (modules/roles/permissions) se obtiene después con GET /api/users/profile. Esto mantiene el token por debajo de 1 KB y evita los errores 431 y 414 al pasarlo por la URL. Ver sección 6.

03 Vía A — Autenticación cruzada por redirección (SSO)

Login centralizado: el usuario se autentica una vez y aterriza en tu aplicación

Este es el patrón que usa crm-educative (plataforma educativa). Tu aplicación no recibe ni valida la contraseña: envía al usuario al login de la plataforma de autenticación y recibe los tokens de vuelta en la URL.

Secuencia del flujo SSO
App externa
1Redirige el navegador a authUrl?redirect_uri=…location.href = authUrl + '?redirect_uri=' + encodeURIComponent(redirectUri)
Plataforma de auth
2Muestra el login y recibe POST /api/auth/login con el redirect_uriEl usuario escribe su correo y contraseña aquí, una sola vez
Plataforma de auth
3Valida el origen contra SSO_ALLOWED_ORIGINSSi el dominio no está en la lista, NO redirige: devuelve el token en el body
Plataforma de auth
4Devuelve la URL con los tokens y el navegador navega a ella{ url: 'https://tu-app…?access_token=…&refresh_token=…' } → location.href = res.url
App externa
5Captura y limpia: guarda los tokens y borra la URL con replaceStateaccess_token → localStorage · refresh_token → sessionStorage
App externa
6Carga el perfil y valida permisos de móduloGET /api/users/profile → valida mod.name === storageKey

3.1 Configuración de la aplicación

Lo primero es declarar dos URLs en tu environment:

// environment.ts
export const ENVIRONMENT = {
  production: false,
  authUrl: 'https://auth.bponet.com.co/login',   // login de la plataforma de auth
  redirectUri: 'http://localhost:4201',          // origen de TU app (sin ruta)
  url: 'https://app.bponet.com.co/auth/api',  // base de la API REST
  storageKey: 'crmEducative',                     // nombre exacto del módulo en auth-ms
};

Basado en platformEducativa/crm-educative/src/environment/environment.ts

Las dos URLs deben ser consistentes entre sí redirectUri es el origen de tu app (sin ruta). El destino exacto se arma después añadiendo la ruta del dashboard. En producción ambos deben coincidir con el dominio registrado en SSO_ALLOWED_ORIGINS.

Paso 2 — Capturar el token en el guard

Tu ruta protegida debe leer access_token de la URL. Es crítico limpiar la URL con replaceState para no dejar el token expuesto en el historial, en los logs del navegador y en el botón "atrás".

async canActivate(route, state) {
  const accessTokenFromUrl  = route.queryParamMap.get('access_token');
  const refreshTokenFromUrl = route.queryParamMap.get('refresh_token');

  if (accessTokenFromUrl) {
    const isValid = await this.processAuthData.proccesAuthData(
      accessTokenFromUrl, refreshTokenFromUrl ?? undefined
    );
    if (isValid) {
      // Limpia el token de la barra de direcciones
      const urlWithoutToken = state.url.split('?')[0];
      this.location.replaceState(urlWithoutToken);
      return true;
    }
    return this.router.parseUrl('/exception/403');
  }

  const token = localStorage.getItem('access_token');
  if (!token || !this.isTokenValid(token)) { this.redirectToLogin(); return false; }

  // Ya está logueado: evita llamadas extra si el módulo está cargado
  if (localStorage.getItem(ENVIRONMENT.storageKey)) return true;

  // Token válido pero sin perfil: cárgalo y valida acceso
  const loaded = await this.processAuthData.loadProfile();
  return loaded ? true : this.router.parseUrl('/exception/403');
}

Decodifica el token (solo lectura, para pintar la UI) y guarda los claims. El refresh token va a sessionStorage: al cerrar la pestaña se descarta, lo que obliga a un login nuevo tras un tiempo de inactividad.

async proccesAuthData(token: string, refreshToken?: string): Promise<boolean> {
  try {
    const decoded = jwtDecode<JwtPayload>(token);

    if (refreshToken) sessionStorage.setItem('refreshToken', refreshToken);

    localStorage.setItem('access_token', token);
    localStorage.setItem('exp',   String(decoded.exp));
    localStorage.setItem('company', String(decoded.company));
    localStorage.setItem('tenantId', String(decoded.tenantId));
    localStorage.setItem('_id',     String(decoded._id));
    localStorage.setItem('email',   decoded.email);
    // … resto de claims

    return await this.loadProfile();   // pide /users/profile y valida módulo
  } catch (error) { return false; }
}

Paso 4 — Cargar el perfil y validar el módulo

El token no trae permisos. Se piden a GET /api/users/profile y se comprueba que el usuario tenga un módulo cuyo name coincida exactamente con tu storageKey. Si no lo tiene, se muestra el mensaje de acceso denegado.

    localStorage.setItem('roles', JSON.stringify(data?.roles || []));

    mod => mod.name === ENVIRONMENT.storageKey
  );

      `No tienes permisos para acceder a esta módulo`,
      `Contacta al administrador del sistema`);
    return false;
  }

  this.saveModuleToLocalStorage(modules);
  return true;
}

Paso 5 — Interceptor: token automático y refresco

Un interceptor añade el Authorization: Bearer a cada petición. Al recibir un 401 refresca el token y encola las peticiones que llegan simultáneamente, para no disparar N refrescos en paralelo.

const token = localStorage.getItem('access_token');

let authReq = req;
if (token && !req.url.includes('/auth/refresh')) {
  authReq = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
}

return next(authReq).pipe(
  catchError((error) => {
    // Rate limit del servidor
    if (error.status === 429) { /* avisar al usuario */ }

    if (error.status === 401 && !req.url.includes('/auth/refresh')) {
      const refreshToken = sessionStorage.getItem('refreshToken');
      if (!refreshToken) { clearSessionAndRedirect(router); return throwError(() => error); }

      if (!isRefreshing) {
        isRefreshing = true;
        refreshTokenSubject.next(null);

        return authService.refreshToken(refreshToken).pipe(
          switchMap((res) => {
            const newToken = res.accessToken || res.access_token || '';
            const newRefreshToken = res.refreshToken || res.refresh_token || refreshToken;

            return from(processAuthData.proccesAuthData(newToken, newRefreshToken)).pipe(
              switchMap((ok) => {
                isRefreshing = false;
                refreshTokenSubject.next(newToken);
                // Reintenta la petición original con el token nuevo
                return from(next(req.clone({
                  setHeaders: { Authorization: `Bearer ${newToken}` } })));
              }),
            );
          }),
        );
      } else {
        // Hay un refresco en curso: esperar y reusar su resultado
        return refreshTokenSubject.pipe(
          filter((t) => t !== null), take(1),
          switchMap((newToken) => next(req.clone({
            setHeaders: { Authorization: `Bearer ${newToken}` } }))));
      }
    }
    return throwError(() => error);
  }),
);

function clearSessionAndRedirect(router) {
  localStorage.clear();
  sessionStorage.clear();
  setTimeout(() => { window.location.href = '/'; }, 500);
}

3.3 La whitelist de orígenes (SSO_ALLOWED_ORIGINS)

Por seguridad, auth-ms solo redirige si el dominio del redirect_uri está registrado. La comparación acepta el dominio exacto y sus subdominios:

const url = new URL(redirectUri);
const isAllowed = this.whitelist.some(domain =>
  url.hostname === domain || url.hostname.endsWith('.' + domain)
);

if (isAllowed) {
  url.searchParams.append('access_token',  result.meta.accessToken);
  url.searchParams.append('refresh_token', result.meta.refreshToken);
  return { url: url.toString(), message: 'Login successful' };
}

Origen: auth-ms/src/auth/auth.controller.ts:109-131

Si tu dominio no está en la lista, el flujo "se rompe" silenciosamente auth-ms no lanza error: simplemente no redirige y devuelve el token en el body de la respuesta. El frontend de la plataforma de autenticación solo hace location.href = res.url si res.url existe; si no, se queda en su propio dashboard y el usuario nunca llega a tu aplicación. Registra tu dominio antes de probar.

Limitación conocida de CORS: x-service-key no está en la lista de headers permitidos En main.ts la configuración de CORS declara allowedHeaders: ['Content-Type', 'Authorization', 'x-idempotency-key']. Eso significa que una llamada desde el navegador (fetch/XHR) con x-service-key será rechazada en el preflight. No afecta a las llamadas desde backend ni al canal TCP. Si necesitas x-service-key desde el frontend, hay que añadirlo a allowedHeaders en auth-ms.

05 Vía C — Conexión TCP

Canal interno optimizado para llamadas entre microservicios

El canal TCP usa JSON sobre un socket persistente, con comunicación request/response por cmd. Es el canal que ya usan educative-backend y api-whatsapp para validar tokens en cada petición y consultar políticas.

import { readFileSync } from 'fs';

function buildTlsOptions(configService: ConfigService) {
  const tlsEnabled = configService.get<string>('TLS_ENABLED') === 'true';
  if (!tlsEnabled) return undefined;

  const keyPath  = configService.get<string>('TLS_KEY_PATH');
  const certPath = configService.get<string>('TLS_CERT_PATH');
  const caPath   = configService.get<string>('TLS_CA_PATH');

  const tlsOptions: Record<string, Buffer> = {};
  if (caPath) tlsOptions.ca = readFileSync(caPath);
  // mTLS: el cliente presenta su propio certificado
  if (keyPath && certPath) {
    tlsOptions.key  = readFileSync(keyPath);
    tlsOptions.cert = readFileSync(certPath);
  }
  return tlsOptions;
}

06 Payload del JWT y contrato de errores

Qué contiene el token y por qué el login puede fallar

6.1 Claims del access token

El token contiene únicamente identidad. No incluye módulos, roles ni permisos:

  return {

    isTrial:  user.isTrial === true,
    trialStartedAt: user.trialStartedAt ?? null,
    trialEndsAt:    user.trialEndsAt ?? null,
    ...(sid ? { sid } : {}),

}

Origen: auth-ms/src/auth/helpers/identity-payload.helper.ts:22-38

Por qué el token es pequeño a propósito Históricamente el JWT incluía el árbol completo de permisos, módulos, rutas e iconos (frecuentemente > 16 KB). Al pasarlo por la URL en el flujo SSO eso provocaba 431 Request Header Fields Too Large y 414 URI Too Long en Node, Nginx y AWS. La separación identidad/autorización lo elimina y reduce el ancho de banda de cada petición.

7.2 Patrón de consumo recomendado

Consultar y cachear

Mantén la config en memoria con TTL de 5–15 minutos por tenantId. No consultes en cada operación de negocio.

Invalidar por versión

Usa version / updatedAt para invalidar la caché cuando el SuperAdmin cambie una política.

Resistir la caída del servicio

Si auth-ms no responde, aplica fail-open (permitir la operación) y deja un log indicando que se usó caché o defaults. Así una caída del servicio de autenticación no detiene tu operación de negocio.

Reportar el consumo

Envía deltas por lote con reportId (UUID) para idempotencia. Calcula el corte mensual en la zona horaria del tenant, no en UTC.

Convención de claves tenantId es el id de la Company (ej. 0000000), no su _id de Mongo. company es el nombre (ej. BPONET).

#PasoResponsableDetalle
1 Registrar los orígenes SSO Equipo auth-ms Añadir tu dominio a SSO_ALLOWED_ORIGINS en el .env de auth-ms (separado por comas) y reiniciar el servicio. Sin esto, la redirección no funcionará.

5 Configurar el frontend Tu equipo Definir authUrl, redirectUri, url y storageKey en tu environment. Ver sección 3.1.
6 Implementar el flujo del frontend Tu equipo Redirección, guard, processAuthData, validación de módulo e interceptor de refresh. Ver sección 3.2.
7 Registrar el cliente TCP (si aplica) Tu equipo Añadir TcpClientModule al AppModule. Ver sección 5.1.
8 Validar la política de CORS Equipo auth-ms Si tu frontend llama por REST, asegurar que tu origen esté en CORS_ORIGIN de auth-ms.

SíntomaCausa probableSolución
431 Request Header Fields Too Large / 414 URI Too Long Token con el árbol de permisos incrustado (legado) o URL de redirección demasiado larga. Usar el token ligero (buildIdentityPayload) y mover la autorización a GET /users/profile.

401 en las peticiones del frontend Access token expirado y el interceptor no encuentra el refresh token. Confirmar que refreshToken está en sessionStorage. Si el usuario cerró la pestaña, deberá iniciar sesión de nuevo (comportamiento esperado).

"No tienes permisos para acceder a esta módulo" storageKey no coincide con el name del módulo, o el usuario no tiene el módulo asignado. Comparar ambos valores (distingue mayúsculas). Asignar el módulo al rol del usuario desde la consola de administración.
CORS bloquea la petición desde el navegador El origen no está en CORS_ORIGIN, o se usa x-service-key (no está en allowedHeaders). Agregar el origen a CORS_ORIGIN. Para x-service-key desde el navegador, añadirlo a allowedHeaders en main.ts.
ECONNREFUSED al puerto 3011 auth-ms no escucha TCP, o host/puerto incorrectos. Verificar MICROSERVICE_HOST/MICROSERVICE_PORT en auth-ms y el firewall. Probar con el script de la sección 5.6.
Login falla con TRIAL_EXPIRED El período de prueba del usuario venció (limits.trialDays o TEST_USER_DAYS). Ampliar la política del tenant o desactivar la marca de prueba del usuario. 0 = sin expiración.
Login falla con COMPANY_BLOCKED La empresa está bloqueada (temporal o indefinidamente). Levantar el bloqueo desde la consola: PATCH /companies/:id/unblock.
429 Too Many Requests Throttling global: 10 req/min por defecto; el login es más estricto (5/min). Aplicar backoff. Mostrar un mensaje al usuario en vez de reintentar en bucle.
